# API 부하 테스트와 HPA 확장 검증

## 환경과 방법

- 검증일: 2026-10-19
- 환경: Mac ARM64, 로컬 k3d rancher-lab
- 대상: 실제 FastAPI 앱의 GET /movies
- 데이터: 테스트 영화 100건 반환
- 경로: 클러스터 내부 k6 → ClusterIP Service → backend → PostgreSQL
- 백엔드 Pod당 CPU: requests 250m, limits 1코어
- 스케줄러 비활성화
- 비교 실험: 목표 30 RPS, 120초, 가상 사용자 100명 사전 할당
- HPA: CPU 목표 50%, 최소 1개·최대 2개, 축소 안정화 300초

## 관측 결과

| 조건 | p95 | HTTP 오류율 | dropped iterations |
|---|---|---|---|
| Pod 1개 | 3.71초 | 0% | 45 |
| Pod 2개 고정 | 8.07ms | 0% | 출력에 표시 없음 |
| Pod 1개 재측정 | 3.54초 | 0% | 36 |
| HPA 1→2개 | 4.93초 | 0% | 417 |
| 확장 완료 후 새 테스트 | 7.76ms | 0% | 출력에 표시 없음 |
| HPA, 연결 재사용 OFF | 3.88초 | 0% | 81 |

HTTP 오류율은 실제 전송한 요청 기준이다.
dropped iterations는 부하 발생기가 예정대로 시작하지 못한 반복 횟수이며,
이 테스트에서는 반복당 HTTP 요청이 하나다.

Pod 2개 고정 실험은 Pod별 CPU 상한은 동일하지만,
백엔드 전체 CPU 상한은 1코어에서 2코어로 증가한다.

## HPA 확장과 요청 분산 조사

기본 연결 재사용 설정의 HPA 실험에서 부하 실행 직전 기록 시각은
18:14:18 UTC였다. 새 Pod의 Ready 상태는 18:15:03 UTC에 최초 관측됐다.
약 45초에는 명령 실행 준비와 주기적 관측 오차가 포함된다.

새 Pod 준비 이후부터 18:16:18 UTC까지의 /movies 접근 로그 집계:
- 기존 Pod: 1,906건
- 새 Pod: 0건

연결 재사용을 끈 진단 실험에서는
18:27:39~18:28:09 UTC의 동일한 30초 구간에:
- 기존 Pod: 355건
- 새 Pod: 331건

이는 연결 재사용이 확장 후 요청 쏠림에 영향을 줬다는 가설을 뒷받침한다.
다만 연결 추적이나 패킷 분석으로 메커니즘을 직접 입증한 것은 아니다.
접근 로그 집계는 클라이언트 측 완료 요청 수와 정확히 일치하지 않을 수 있다.

## 결론

- Pod 1개에서 지연 증가와 CPU 상한 부근의 사용량이 반복 관측됐다.
- Pod 2개를 미리 준비한 두 실험에서는 p95가 약 8ms였다.
- HPA의 1→2개 자동 확장은 성공했다.
- 자동 확장 성공만으로 전체 테스트 구간의 성능 개선이 보장되지 않았다.
- 연결 재사용 OFF 실험에서 새 Pod의 요청 처리를 확인했다.
- 연결 재사용 OFF는 원인 조사용 조건이며 운영 권장 설정으로 제시하지 않는다.

## 한계

- Mac의 CPU·메모리를 공유하는 로컬 환경이다.
- 소규모 합성 데이터와 단일 조회 API를 사용했다.
- 전체 p95에는 확장 전·대기·확장 후 구간이 섞여 있다.
- 확장 후 구간만의 p95는 별도로 측정하지 않았다.
- 실험별 확장 시점과 로컬 자원 상태가 달라 단일 요인의 개선율을 확정할 수 없다.
- CPU 급증의 앱 내부 원인은 미확정이다.
- EKS 성능이나 운영 환경의 처리 한계로 일반화하지 않는다.
